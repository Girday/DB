# Лабораторная работа №2

SQL-запросы и аналитика для базы поликлиники. Вариант 7, PostgreSQL 17.

Работа продолжает ЛР1: пациенты записываются к врачам на услуги. Используем пять таблиц — `patients`, `doctors`, `specialties`, `services`, `appointments`. Структуру для второй лабораторной не меняли.

## Файлы и задания

| Задание | Файл | Что делаем |
|---|---|---|
| 1.1 | [01_data.sql](01_data.sql) | Добавляем пациентов, врачей, услуги и приёмы |
| 1.2 | [02_dml.sql](02_dml.sql) | Добавляем связанные строки, меняем статус и тарифы, удаляем ошибочную запись, выполняем ROLLBACK |
| 2.1 | [03_joins.sql](03_joins.sql) | Выводим журнал приёмов, врачей без записей и пациентов с платной записью к неврологу |
| 2.2 | [04_aggregates.sql](04_aggregates.sql) | Считаем приёмы по врачам, стоимость по пациентам и показатели по месяцам и специальностям |
| 3.1–3.4 | [05_subqueries.sql](05_subqueries.sql) | Сравниваем тариф со средним своей специальности, используем EXISTS и NOT EXISTS, находим последний завершённый приём |
| 4 | [06_report.sql](06_report.sql) | Собираем отчёт по специальностям через CTE |
| Проверка данных | [07_checks.sql](07_checks.sql) | Выводим количества строк, статусы, месяцы, повторные обращения и сущности без приёмов |

Для частей 2–4 нужно объяснить 11 запросов. В части 4 под отчётом понимается результат SQL-запроса; отдельный документ оформлять не требуется.

## Данные

После исходных `lab1/schema.sql` и `lab1/data.sql` выполняем `01_data.sql` один раз. Добавляем 20 пациентов, 4 врачей, 6 услуг и 72 приёма. Исходные строки сохраняем.

| Таблица | Строк после заполнения |
|---|---:|
| patients | 24 |
| doctors | 8 |
| specialties | 3 |
| services | 12 |
| appointments | 80 |
| Всего | 127 |

Приёмов за сентябрь — 24, за октябрь — 32, за ноябрь — 24. Используем статусы `scheduled`, `completed`, `cancelled`. Даты и статусы фиксированы, поэтому результаты можно повторить независимо от дня запуска.

В наборе есть несколько ситуаций для проверки запросов:

- Пациенты с картами `ЛР2-019` и `ЛР2-020` не записывались на приём.
- У врача Оксаны Петровны Лазаревой нет записей.
- Пациенты `ЛР2-006`, `ЛР2-012`, `ЛР2-018` имеют только отменённые приёмы.
- Услугу «Расширенная неврологическая диагностика» пока никто не получал.
- Есть бесплатные услуги и повторные обращения. Старый приём офтальмолога стоит 1000 рублей при текущем тарифе 1500.

В исходной модели у столбцов есть ограничение NOT NULL. NULL получаем в результатах: например, после LEFT JOIN для врача без записей или при поиске последнего завершённого приёма пациента, у которого таких приёмов нет. Нулевая цена означает бесплатную услугу.

При заполнении находим идентификаторы через JOIN. ФИО новых врачей служат метками тестового набора; в самой модели ФИО не является уникальным ключом. Повторная загрузка нарушит уникальность номеров карт. Весь файл выполняем одной транзакцией.

## Расчёты

Стоимость оказанных услуг считаем по `appointments.charged_price` только для `completed`. Так учитываем цену, согласованную при записи. Текущий тариф храним в `services.price`. Отдельной таблицы платежей в базе нет, поэтому по этим данным нельзя определить фактическую оплату.

В среднюю стоимость включаем бесплатные завершённые приёмы. Если завершённых приёмов нет, получаем NULL.

В запросе 2.2.3 задаём три месяца через CTE `months`: для каждого указываем начало и начало следующего месяца со смещением `+03`. Приём относится к интервалу, если его начало не раньше первой границы и строго раньше второй. В результат попадают только месяцы и специальности с завершёнными приёмами. Отображение времени начала месяца зависит от часового пояса клиента.

В `06_report.sql` выполняем расчёты по этапам:

1. В `source_data` отбираем приёмы за сентябрь–ноябрь и получаем специальность услуги.
2. В `totals` считаем все записи по специальности. В `completed`, `cancelled` и `scheduled` отдельно отбираем статусы и группируем строки. Для завершённых приёмов считаем сумму и среднее.
3. В `cancellation_rates` делим число отмен на общее число записей и умножаем на 100. Здесь используем группы из `totals`, в которых уже есть хотя бы один приём, поэтому знаменатель положителен.
4. Через LEFT JOIN присоединяем показатели к справочнику специальностей. Отсутствующие количества и суммы заменяем нулём через COALESCE. Для специальности без записей оставляем NULL в доле отмен и среднем.

В знаменатель доли отмен входят и запланированные приёмы. По этому показателю сравниваем текущее состояние записей за выбранный период.

В проверочном файле используем обычные SELECT. По результатам проверяем требования задания: минимум 100 строк суммарно, 30 приёмов, три статуса и три месяца. Там же смотрим повторные обращения, бесплатные услуги и отсутствие приёмов. Число несовпадений специальностей врача и услуги должно быть нулевым.

## Запуск в учебной базе

### Через run.sh

[run.sh](run.sh) запускает контейнер PostgreSQL через Docker Compose, ждёт его готовности и выполняет выбранные SQL-файлы в рабочей базе `clinic_lab1`. При ошибке выполнение останавливается. Для запуска нужен работающий Docker и настройки подключения из ЛР1.

Из папки `lab2`:

| Команда | Что выполняется |
|---|---|
| `sh run.sh` или `sh run.sh queries` | Все 11 запросов из файлов 03–06 |
| `sh run.sh data` | `01_data.sql`: однократное дополнение данных |
| `sh run.sh dml` | `02_dml.sql`: изменения с последующим ROLLBACK |
| `sh run.sh checks` | `07_checks.sql`: проверки данных |
| `sh run.sh joins` | `03_joins.sql`: JOIN-запросы |
| `sh run.sh aggregates` | `04_aggregates.sql`: группировки и агрегаты |
| `sh run.sh subqueries` | `05_subqueries.sql`: подзапросы |
| `sh run.sh report` | `06_report.sql`: CTE-отчёт |

Из корня репозитория используем, например, `sh lab2/run.sh checks`: скрипт сам переходит в свою папку.

Без аргумента выполняются только запросы, данные не добавляются. Режим `data` меняет рабочую базу; повторная загрузка приведёт к ошибке уникальности. Скрипт не создаёт таблицы и не применяет миграции. Перед загрузкой данных после изменения схемы ЛР1 нужно проверить совместимость SQL с актуальной структурой.

### Прямые команды Docker

Команды выполняем из корня репозитория при работающем контейнере `db-lab1-postgres`. Перед загрузкой сверяем структуру с `lab1/schema.sql`: SQL рассчитан на исходные пять таблиц. После изменения модели на защите ЛР1 потребуется учесть новые связи и обязательные поля.

Дополнение данных загружаем один раз:

```sh
docker exec -i db-lab1-postgres psql -X -U lab1_user -d clinic_lab1 --set=ON_ERROR_STOP=1 --file=- < lab2/01_data.sql
```

Для просмотра запросов подключаемся к psql:

```sh
docker exec -it db-lab1-postgres psql -X -U lab1_user -d clinic_lab1
```

Копируем нужный запрос из файлов `03_joins.sql`–`06_report.sql` и выполняем его. Проверки данных можно запустить целым файлом:

```sh
docker exec -i db-lab1-postgres psql -X -U lab1_user -d clinic_lab1 --set=ON_ERROR_STOP=1 --file=- < lab2/07_checks.sql
```

Параметр клиента `--set=ON_ERROR_STOP=1` останавливает выполнение файла при ошибке. В самих SQL-файлах команд настройки psql нет.

Для демонстрации изменений отдельно запускаем:

```sh
docker exec -i db-lab1-postgres psql -X -U lab1_user -d clinic_lab1 --set=ON_ERROR_STOP=1 --file=- < lab2/02_dml.sql
```

В `02_dml.sql` открываем транзакцию через BEGIN и в конце выполняем ROLLBACK. Поэтому дополнительная транзакция и параметр `--single-transaction` для этого файла не нужны. После отката получаем прежние строки и тарифы. Значения последовательностей IDENTITY назад не возвращаются: после временных вставок в ID могут остаться пропуски.

## Автоматическая проверка

`verify.py` — вспомогательный Python-скрипт для проверки решения. Задание лабораторной его не требует. Для запуска нужны Python 3, Docker и образ `postgres:17.11`:

```sh
python3 lab2/verify.py
```

При таком запуске проверяем SQL в отдельном временном контейнере с исходной схемой ЛР1. Скрипт сверяет 11 запросов с расчётами Python, сохранность исходных строк, действия DML и откат. Дополнительно проверяет пустые группы, повторную загрузку и границы месяцев при другом часовом поясе. После проверки он удаляет контейнер; рабочую `clinic_lab1` не использует.

Полные результаты запросов и сводная таблица находятся в [results](results/README.md). Числа в них относятся к исходному тестовому набору.
