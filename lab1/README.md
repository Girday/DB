## Принятая модель ЛР №1

ЛР №1 сдана без оценки. Полная итоговая схема: [er_diagram_approved.md](er_diagram_approved.md).

Приём связан с конкретной записью о работе врача: `appointments → employment_records → hospitals`, а врач определяется через `employment_records → employment_books → doctors`. Прямых ссылок на врача и больницу в приёме нет. В истории работы хранятся должность, зарплата и даты трудоустройства и увольнения.

Файлы относятся к двум последовательным состояниям базы:

- [schema.sql](schema.sql), [data.sql](data.sql), [constraints_test.sql](constraints_test.sql) и [er_diagram.md](er_diagram.md) — исходная модель из пяти таблиц;
- [migration.sql](migration.sql) — однократный переход от исходной модели к утверждённой модели из восьми таблиц;
- [er_diagram_approved.md](er_diagram_approved.md) — структура после миграции, включая все таблицы и связи.

ЛР №2 подготовлена на исходной модели. Её файлы не адаптировались к новой схеме. Старые `data.sql` и `constraints_test.sql` используют `appointments.doctor_id` и предназначены для запуска до миграции.

## Что делает миграция

Миграция рассчитана на структуру из `schema.sql`; новые таблицы ещё не должны существовать. Все изменения выполняются в одной транзакции. Повторный запуск на уже мигрированной базе не предусмотрен.

1. Создаёт больницы, книжки врачей и записи о работе.
2. Для переноса исходных данных создаёт больницу «Исходная поликлиника» с адресом «Адрес не указан», книжку и одну запись о работе с должностью «Врач» для каждого существующего врача. Это явное правило переноса из прежней модели одной поликлиники, а не установленные сведения о реальных местах работы. Адрес нужно уточнить; неизвестные зарплаты и даты трудоустройства сохраняются как NULL.
3. Добавляет в приёмы ссылку на запись о работе и заполняет её через прежний `doctor_id`. Затем устанавливает NOT NULL и внешний ключ. Пациент, врач, услуга, время, статус и зафиксированная цена каждого старого приёма сохраняются.
4. Удаляет две прежние проверки и их функции, обращающиеся к удаляемому `appointments.doctor_id`. Новых триггеров или функций не создаёт.
5. Удаляет `doctor_id` из приёмов. Его старый внешний ключ и индекс PostgreSQL удаляет вместе со столбцом. Остальные исходные таблицы и данные сохраняются.

Зарплата может быть неизвестна, но известная зарплата неотрицательна. Дата увольнения допустима только вместе с датой трудоустройства и не раньше неё. Если дата увольнения отсутствует, это означает лишь отсутствие указанной даты. У врача может быть не более одной книжки; для новых врачей её добавляют явно. Повторная работа в той же больнице допускается отдельной записью.

В принятом варианте без новых триггеров и индексов не проверяются соответствие специальности врача услуге, попадание приёма в период работы и одновременная запись одного врача. Изменение специальности врача также больше не блокируется наличием приёмов. Исходная защита специальности используемой услуги сохраняется. Внешние ключи, ограничения цен и статусов, обязательность полей и запреты удаления связанных строк продолжают действовать.

Проверено 01.11.2026 на PostgreSQL 17.11 в отдельном одноразовом контейнере: переход к восьми таблицам, сохранение всех восьми исходных приёмов и их врачей, неизменность остальных исходных данных, 13 отрицательных проверок ограничений, добавление новой больницы, записи о работе и приёма. Отдельно проверен переход без исходных тестовых данных. Рабочая база не использовалась.

## Запуск PostgreSQL

Конфигурация: [compose.yaml](compose.yaml). Используется [официальный образ PostgreSQL](https://hub.docker.com/_/postgres) версии 17.11.

Параметры подключения с компьютера:

- адрес: `127.0.0.1`;
- порт: `5433`;
- база данных: `clinic_lab1`;
- пользователь: `lab1_user`;
- пароль: значение `POSTGRES_PASSWORD` в `.local/lab1_postgres.env`.

Файл `.local/lab1_postgres.env` исключён из Git. Для первоначального запуска в новом checkout его нужно создать с переменными `POSTGRES_USER=lab1_user`, `POSTGRES_DB=clinic_lab1` и `POSTGRES_PASSWORD` с выбранным паролем.

Структура базы и данные хранятся в томе Docker `db-lab1-pgdata`, отдельно от контейнера. При замене контейнера той же версией PostgreSQL и подключении прежнего тома база сохраняется. Обычная остановка контейнера также не удаляет базу. Часовая зона сервера — `Europe/Moscow`.

Команды выполняются из корня репозитория:

```sh
docker compose --project-name db-lab1 --file lab1/compose.yaml up --detach --wait
```

Для интерактивного подключения через клиент `psql` внутри контейнера:

```sh
docker exec -it db-lab1-postgres psql -U lab1_user -d clinic_lab1
```

В `psql` команда `\dt` показывает таблицы, `\q` завершает подключение.

Для первоначального создания структуры в пустой базе:

```sh
docker exec -i db-lab1-postgres psql -X -U lab1_user -d clinic_lab1 --set=ON_ERROR_STOP=1 --single-transaction --file=- < lab1/schema.sql
```

Для первоначального заполнения таблиц после создания структуры:

```sh
docker exec -i db-lab1-postgres psql -X -U lab1_user -d clinic_lab1 --set=ON_ERROR_STOP=1 --single-transaction --file=- < lab1/data.sql
```

## Запуск проверок ограничений

После заполнения базы:

```sh
docker exec -i db-lab1-postgres psql -X -U lab1_user -d clinic_lab1 --file=- < lab1/constraints_test.sql
```

| Код ошибки | Причина |
|---|---|
| `23502` | Нарушение `NOT NULL` |
| `23503` | Нарушение внешнего ключа, в том числе запрет удаления связанной строки |
| `23505` | Нарушение уникальности |
| `23514` | Нарушение `CHECK` или бизнес-правила с этим кодом в `RAISE EXCEPTION` |
